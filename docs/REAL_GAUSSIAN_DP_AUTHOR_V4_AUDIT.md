# TimeEval: проверка Gaussian DP для всех пяти Adapted-алгоритмов — 17.10.2026

## Состояние реализации

- Реализованы отдельные **record-level Gaussian aggregate DP server-proxy variants** для пяти `Adapted` методов: FKM, FKDC, HF_DBSCAN, NN-FC и p-FClus. Они теперь проходят один и тот же UI-эксперимент совместно с тремя существовавшими NumPy-методами.
- **Это НЕ прежние оригинальные авторские алгоритмы.** Их приватно-зависимые локальные вычисления изменены: DP count+sum на клиенте перед оригинальной серверной стадией. Для p-FClus исключена приватно-зависимая локальная персонализация; для HF_DBSCAN применяется публичная двумерная проекция и отдельный зашумлённый подсчёт ячеек.
- Пользователь видит названия `Adapted ... [DP proxy]` и backend `author-server DP proxy` в UI/Excel. Privacy=None по-прежнему выполняет старые алгоритмы без изменений.
- Проверка: **168 passed, 5 skipped**. CLI проверен в режиме `--backend all` на реальных Digits.
- Проведено **288 результатов** с Iris, Wine и Digits в комбинациях, описанных ниже. **Dry Bean 13 611×16 пока НЕ подтверждён**: официальный ARFF недоступен в изолированном окружении. Отдельно прошёл нагрузочный тест 13 611×16 на явных СИНТЕТИЧЕСКИХ blobs; это лишь проверка масштабирования, а не Dry Bean.

## Протокол измерений и свойства входных данных

Контроль — `public_clipped_control` (публичная фиксированная нормализация + C=4, без шума). DP — `gaussian_dp_aggregate`, ε=20/10/5/1, δ=1e-5, C=4; 10 клиентов, IID, 100% participation, 0% dropout, requested 20 раундов. В Iris испытаны только контроль и ε=20. Использованы seeds 42, 43, 44; при каждом запуске шум генерировался независимо криптографическим генератором.

За счёт независимого OS CSPRNG одни и те же benchmark seeds **не повторяют DP шум**. Три seeds недостаточны для статистически подтверждённого ранжирования. По реальным данным фактическая доля строк с отсечённой L2-нормой при C=4 составила Iris **0%**, Wine **24,2%**, Digits **100%**. Это существенно для корректного толкования: даже matched контроль на Digits уже искажает признаки; нельзя приписывать разницу с обычным Privacy=None одному только шуму.

## Интерпретация

1. **Методы различаются по чувствительности.** На Wine в данном эксперименте p-FClus DP proxy показал средний ARI 0,642 при ε=20 против 0,840 в matched контроле, а FKM DP proxy — 0,234 против 0,915. На Digits DP proxy FKDC, NN-FC и p-FClus сохранили ненулевое качество, но FKM сильно ухудшился. Это исследовательские наблюдения, а не доказательство статистического превосходства.
2. **HF_DBSCAN DP proxy остаётся проблемой.** На Wine/Digits многие сценарии вырождаются, и ARI ≈ 0 нельзя представлять как успешно сохранённое качество. Это ограничение текущей модифицированной плотностной модели, требующее отдельной исследовательской разработки. Никакой «автоматической» гарантийной починки качества здесь не заявляется.
3. **При ε=1 все алгоритмы испытывают значительное давление от шума, но связь ε с качеством не обязана быть монотонной на трёх seeds.** Ещё одна причина не ранжировать алгоритмы по единичным запускам.
4. **20 раундов FKM не эквивалентны одному раунду FKDC/NN-FC/p-FClus/HF_DBSCAN.** FKM распределяет ε по раундам, одноразовые адаптеры расходуют бюджет однократно; у HF_DBSCAN ε делится ещё пополам между выбором кандидатных представителей и счётчиками ячеек.

## Строгие границы приватности

Математически калиброванный шум покрывает только описанный механизм выпуска **ограниченных агрегированных статистик**. Обычное публичное seed НЕ определяет шум. У агрегирования FKM применяется базовая последовательная композиция по всем 20 раундам; при непересекающихся клиентах — параллельная композиция в каждом раунде. HF_DBSCAN тратит часть бюджета на DP-представителей и часть на DP-счётчики. Весь Excel/JSON/history остаётся **НЕ DP**: отчёт использует исходные метки и признаки, выдает class counts, hashes, локальные показатели и диагностические утечки. Без secure aggregation сервер может видеть незащищённые промежуточные статистики в общей симуляции. Multiple algorithms and repeated runs compose: 8 algorithms with ε=20 each yield conservative ε≤160, δ≤8e−5 *per full set of runs*, not an ε=20 report.

- Получить настоящий `Dry_Bean_Dataset.arff` (13 611×16, 7 классов) — без него реальной проверки Dry Bean не было. Ни одна синтетическая выборка не засчитывается вместо него.
- Провести paired clipping-control/ε=20/10/5/1 на реальном Dry Bean для всех 8 NumPy+Adapted вариантов, минимум 10 seeds и проверку реального процента клиппирования; сохранить результаты, в том числе вырожденные.
- Запустить Flower/Ray на доступном Windows/Flwr окружении, поскольку только NumPy+Adapted были реально исполнены здесь.
- Не заявлять DP-сертификацию всего TimeEval без отдельного threat model, privacy-safe экспорта, учёта затрат по всем экспериментам и независимой ревизии доказательств.

## Как воспроизвести на Windows

Из корня проекта: `python tools/benchmark_dry_bean_gaussian_aggregate.py --arff "C:\path\Dry_Bean_Dataset.arff" --backend all --clip 4 --epsilons 20 10 5 1 --seeds 42 43 44`. Встроенный скрипт проверяет SHA-256, реальный размер, количество признаков/классов и записывает метрики и историю, не заменяя датасет искусственными данными.

Подробная методология: `docs/GAUSSIAN_AUTHOR_DP_V4.md`.
