# Планирование локальных серий

Файл плана описывает входные данные и научные условия до обучения. Рабочий пример на Iris содержит два benchmark seed, локальные методы и два федеративных сценария. [План Iris](../configs/series/pilot.yaml)

Из корня рабочего checkout с подготовленным окружением Windows можно проверить пример, затем сохранить его полное раскрытие.

```powershell
& '.\.venv\Scripts\clustereval.exe' series validate '.\configs\series\pilot.yaml' --json
& '.\.venv\Scripts\clustereval.exe' series plan '.\configs\series\pilot.yaml' --output '.\results\resolved_plan.json' --json
```

Проверка загружает входы и сверяет их идентичность. Алгоритмы кластеризации и симуляции не запускаются. Успешная проверка возвращает код 0. При ошибке ввода команда возвращает 2 и пишет диагностику в stderr. `series plan` без `--output` выдаёт полный JSON в stdout. При `--output` файл публикуется заменой после проверки. Запись в сам входной план, входные данные или выбранный для импорта исторический архив отклоняется.

## Обычный план v1

Исходный YAML или JSON имеет поле `format: pyclusteval.plan.v1`. Ключи объектов должны быть уникальными строками. Допускаются только конечные значения типов JSON. Для одинаковых повторяющихся структур YAML используй явные ссылки серии на именованный сценарий. YAML-алиасы не входят в синтаксис v1.

| Поле | Значение |
|---|---|
| campaign | Обязательное name, необязательные description и output_dir. Каталог вывода по умолчанию совпадает с именем кампании и разрешается относительно файла плана. |
| datasets | Словарь по имени в плане. Каждый элемент описывает registry-провайдер или NPZ с точными входными массивами. |
| scenarios | Словарь по имени. Каждый сценарий указывает mode, упорядоченный список algorithms и поддерживаемые научные параметры. Для проверки размера и протокола каждый объявленный сценарий должен использоваться хотя бы одной серией. |
| series | Список объектов с name, dataset, целочисленным seed и упорядоченным списком scenarios. Имя серии уникально. |
| execution | Необязательные параметры запуска и границы ресурсов. |
| export | Для обычного плана profile=general и verify_checksums=true. |

Регистровый вход, например Iris, задаётся `{provider: registry, name: iris}`. Для Blobs можно задать params и preparation_seed. NPZ задаётся через provider=npz и path. Допустимые поля проверки включают expected_shape, sha256 для файла и x_sha256/y_sha256 для байтов массивов. Путь к входным данным разрешается относительно файла плана. Фиксированный датасет сохраняет одинаковые объекты при изменении seed серии. PLAN останавливается, если данные недоступны локально.

Обычное сравнение принимает один или несколько алгоритмов. В федеративном сценарии требуется явное поле `stopping_profile`. Значение `current_gui` выбирает политику остановки текущего приложения, `historical_paper` обозначает политику исторической статьи. Локальные сравнения обходятся без этого поля. Выбор сохраняется в научных условиях и меняет идентификаторы. Подтверждение вычислительной совместимости исторического профиля относится к этапу исполнения.

`algorithm_params_by_name` содержит явные параметры конкретного метода. `grid` описывает альтернативы конкретного параметра. Например, в сценарии с K-Means следующий фрагмент задаёт два задания.

```yaml
grid:
  kmeans:
    n_init: [2, 4]
```

Внутри метода применяется декартово произведение его осей. Обычное list-значение вне grid остаётся одним значением и проверяется по типу поля. В частности, expected_shape=[150, 4] относится к одному датасету. Параметр, для которого адаптер ожидает скаляр, отклонит список. Служебные расписания и конфигурацию механизма DP нельзя задавать произвольными overrides.

`execution` по умолчанию задаёт processes=1, blas_threads=1, max_retries=0, failure_policy=continue и profile=cold. Необязательные timeout_sec, total_time_sec и memory_limit_mb по умолчанию равны null. Допустимая альтернативная политика ошибок — stop. Профиль процесса warm остаётся заявкой для будущей проверки backend. Операционные тайм-ауты, число технических попыток и каталог результатов не меняют научный job_id. В JSON-резюме проверки и полном раскрытии execution_readiness содержит status=not_checked и перечень запрошенных пар backend/lifecycle. Успешная статическая валидация плана не подтверждает работоспособность симуляции или жёсткого лимита памяти.

## Идентичность и раскрытие

Результат имеет format=pyclusteval.resolved-plan.v1 и содержит datasets, series, comparisons, jobs, execution, export, source_id и counts. Каждое задание связано с исходной серией через (series, run_id) и со сравнением через comparison_id. В раскрытии сохраняются общие условия, backend, передаваемые параметры и их происхождение. Величины, вычисляемые только из данных на следующем этапе, отмечаются правилом их получения.

Источник кода определяется в реально импортированном checkout через API [захвата снимка](EXPERIMENT_SOURCE_CAPTURE.md). Содержимое одинаковых исходников сохраняет один source_id при переносе. Планировщик вычисляет SHA-256 от компактного UTF-8 JSON массива [версия идентичности, тип, данные], с отсортированными ключами объектов и исходным порядком списков. Общий input_id связывает научный протокол, dataset_id, seed и source_id. job_id дополнительно учитывает метод, backend, его фактические параметры и профиль исполнения. comparison_id связывает общий input_id и отсортированный список job_id. Это позволяет добавлять метод к сравнению при неизменных общих входах без переименования задания другого метода. При изменении общих условий, например обусловленного методами минимума объектов на клиента, меняются все затронутые задания. В input-DP все варианты конкретного сравнения используют одну release, поэтому их состав и параметры также участвуют в общем input_id. Фактический fingerprint release появится при подготовке данных. Повтор идентичного задания под другим названием диагностируется.

## Импорт и миграция

```powershell
& '.\.venv\Scripts\clustereval.exe' series import-archive 'X:\paper\experiments' --output '.\results\paper-plan.json' --json
& '.\.venv\Scripts\clustereval.exe' series migrate '.\configs\example.yaml' --output '.\results\migrated.json' --json
```

После успешной записи применяй `series validate` и `series plan` к полученному файлу. Исторический вариант привязан к архивным входам, их хэшам, внешним идентификаторам и проверяемому протоколу. Относительный historical.path в файле раскрытого плана отсчитывается от каталога опубликованного файла; при выводе в stdout — от каталога исходного плана. Пути dataset, partition и прочих членов архива отсчитываются от historical.path. При публикации на другом диске Windows этот локатор становится абсолютным. Для переноса между дисками снова укажи доступное расположение архива. Неподдержанный или противоречивый архив даст диагностику; импорт не исполняет код из статьи.

Миграция раскрывает старые list-сетки и сохраняет запись каждого задания с профилем legacy-run.v1. Старые относительные пути отсчитываются от рабочего каталога запуска команды migrate. Запускай миграцию из каталога, из которого запускался исходный CLI. Перенос нового файла с относительными ссылками предполагает перенос соответствующих входов. Для Blobs и MNIST 10k унаследованный из benchmark seed параметр подготовки записывается явно. Выборки с разными seed сохраняют раздельную идентичность. Одинаковые repetitions со старым seed вызывают диагностическую ошибку. Миграция сохраняет переданное адаптеру словарное представление, включая разные legacy-значения k и n_clusters и исходный benchmark K. У старого runner отсутствует общий schedule, поэтому явный rounds, в том числе выше 10, сохраняется. Параметры и их приоритеты, метрики, разбиение даже в local, а также старый порядок запуска сохраняются в раскрытии. Для legacy-федеративного задания отдельно указывается stopping_profile=legacy_run. После миграции исполнение требует поддержки именно этого профиля. Прежняя команда `clustereval run CONFIG` продолжает пользоваться прежним маршрутом.

Минимальный исходный файл для проверки миграции:

```yaml
datasets: [{name: iris}]
algorithms: [{name: kmeans}]
metrics: [ari]
```
