# Запуск и восстановление локальной кампании

Для запуска нужен рабочий checkout с подготовленным окружением Windows и план `pyclusteval.plan.v1`. Обычный и мигрированный планы задают каталог кампании через `campaign.output_dir`, относительно файла плана. Каталог должен быть новым или пустым. Запуск идёт в текущем терминале. Каждый алгоритм получает свежий процесс. На этом этапе поддержан профиль `cold` с `processes: 1`.

```powershell
& .\.venv\Scripts\python.exe -m clustering_eval.cli series run .\configs\series\pilot.yaml --json
& .\.venv\Scripts\python.exe -m clustering_eval.cli series status .\results\iris-pilot --json
& .\.venv\Scripts\python.exe -m clustering_eval.cli series resume .\results\iris-pilot --json
& .\.venv\Scripts\python.exe -m clustering_eval.cli series retry .\results\iris-pilot --status timeout --timeout-sec 120 --json
```

`status` можно вызвать во втором терминале. В сводке есть `planned`, счётчики по всем восьми статусам, последнее зарегистрированное `current`, признак удержания управляющей блокировки (supervisor или наблюдатель, завершающий его дерево), последняя ошибка и причина остановки. `elapsed_sec` показывает календарное время с момента создания. `report_path` равняется `null`, пока отдельного файла отчёта нет. Значение `worker_liveness: unconfirmed` означает, что status не удостоверяет продолжение работы самого алгоритма. После закрытия терминала или перезагрузки открой статус и выполни resume. Состояние переживает завершение процесса. Для мягкой остановки используй Ctrl+C.

`resume` перепроверяет планы, снимок кода, данные, подготовку и предыдущие принятые результаты. Если worker успел опубликовать целый результат перед аварией supervisor, resume проверяет его и может принять без пересчёта. Осиротевшая незавершённая попытка получает `interrupted`. Исполнитель продолжает задания `pending`, `interrupted`, `cancelled`. После отказа `failure_policy: stop` новый явный resume может приступить к оставшимся pending. В смешанной кампании неподдерживаемый backend получает `skipped` с причиной. Политика `continue` разрешает выполнить следующие поддержанные задания. `warm`, параллельный запуск и исполнение `historical_reference/persistent_worker` отклоняются перед стартом заданий. Планирование и подготовка исторических входов доступны через прежние инструменты.

**Повторы.** Правила `execution.max_retries` действуют на дополнительные автоматические попытки отдельного задания за всю кампанию, в том числе после повторного открытия. Значение по умолчанию — 0. Явный `retry --status error` или `retry --status timeout` выделяет каждому подходящему заданию одну новую попытку за вызов. Опция `--job-id ID` ограничивает выбор одним научным заданием. Значение `attempts_started: 0` указывает на отсутствие новых запусков.

**Лимиты.** `timeout_sec` ограничивает один процесс задания с запуска до выхода. `total_time_sec` отсчитывается от первой активации и включает простой; завершение общего бюджета сохраняет оставшиеся задания. В resume/retry можно передать `--timeout-sec`, `--total-time-sec`, `--memory-limit-mb`. Значение `none` снимает соответствующий лимит. Начальная точка общего срока сохраняется при продлении. В журнале каждой сессии доступны UTC и действовавшие лимиты. На Windows ограничения численных потоков передаются через `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS` до запуска интерпретатора worker. Эффективная конфигурация видна по наблюдениям в результате. При запросе жёсткого лимита памяти исполнитель проверяет возможность его применения до вычисления. Сведения о фактически поддержанном ограничении относятся к конкретному механизму Windows.

В Windows краткоживущий служебный наблюдатель может сопровождать вычислительное дерево и дождаться его остановки при аварии supervisor. Его работа входит в техническое время запуска. Измерение времени алгоритма и жёсткий лимит памяти вычислительного дерева относятся к worker и его потомкам.

**Совместимость среды при продолжении.** Перед новой подготовкой или попыткой `resume` и `retry` сверяют реализацию и версию Python, семейство ОС, архитектуру и версии NumPy, SciPy, scikit-learn с данными создания кампании и прежних попыток. Путь к интерпретатору и версии служебных пакетов, например packaging, могут меняться. После исполнения или возможного старта Flower дополнительно сверяются версии Flower, Ray, grpcio, grpcio-health-checking и protobuf. Для впервые исполняемого Flower действует отдельный допуск проверенной среды. Новая установка Flower в совместимую venv допускается. Ранее пропущенный job сохраняет конечный статус `skipped` по обычным правилам очереди.

При расхождении или неизвестной обязательной версии команда возвращает код 3, сообщает значения в `environment_differences` и сохраняет причину в последней сессии. Старые записи можно читать и экспортировать. Для их продолжения используются доступные версии из снимка создания, сведения сессий и worker, в том числе численные версии из принятых отчётов. Для первой сессии `run` доступен снимок создавшего её процесса. Если у более поздней попытки отсутствуют необходимые сведения, причина называет пробел. Чтение `status`, экспорт и проверка архива не требуют повторного запуска методов. Сопоставление этих полей не удостоверяет идентичность оборудования, BLAS и всех бинарных сборок.

**Коды завершения**

| Код | Значение |
|---|---|
| 0 | Успешное чтение status либо все запланированные задания имеют принятый результат. |
| 2 | Неверный план, аргумент, неподдерживаемый общий профиль или лимит. |
| 3 | Кампания неполна, другой supervisor владеет каталогом, run попал в существующую кампанию или файловая операция прервала выполнение. |
| 4 | Нарушена целостность сохранённых данных, журнал отсутствует/нечитаем либо создание кампании осталось незавершённым. |

**Каталог и ошибки.** `raw/` содержит исходный план, раскрытие и снимок кода. `state/journal.sqlite` связывает научные задания с техническими попытками, сессиями и подготовленными сравнениями. В `attempts/<id>/` находятся запрос, stdout.log, stderr.log и фактически опубликованные данные. `cache/` содержит доверенные массивы и соседние reservation-файлы. Сохраняй эти каталоги вместе. Удаление подготовленного выпуска input-DP или его reservation лишает исполнителя оснований для продолжения. При повреждении верни проверенные исходные байты. Если восстановление невозможно, укажи отдельную новую кампанию и учти возможность прежних выпусков. Если обычная подготовка прервалась до публикации и целый результат ещё не был закреплён, resume сохранит частичные файлы в `cache/<comparison_id>.incomplete-<id>/` и повторит подготовку по проверенным входам. При нехватке диска освободи место, затем проверь status и вызови resume. Сохрани stderr, если диск не позволил записать диагностику в журнал. Если прервалась начальная публикация и остался `.pyclusteval-initializing`, используй отдельный пустой каталог для нового run. Worker до завершения инициализации не запускается.

**Чтение для экспорта.** `clustering_eval.experiments.runner_reader.read_campaign(Path(root))` открывает согласованный срез `pyclusteval.campaign-reader.v1` из сохранённых материалов. В `jobs` лежат исходное задание, состояния, причины, все попытки и необязательная `accepted`. Каждый `accepted.directory` относится к корню кампании, пути в `accepted.candidate.result` и `accepted.candidate.labels` относятся к этому каталогу. Кандидат включает нативный отчёт, метаданные COMPUTE и хэши файлов. Для проверки повреждённого успеха смотри `recorded_status`, `status`, `integrity_errors` и `accepted`. Другие целые задания остаются доступны. Логи и подготовка могут содержать приватные данные исследования. Для aggregate-DP сведения обо всех попытках, включая неизвестные исходы, читать вместе с областью применимости отчёта успешной попытки.
