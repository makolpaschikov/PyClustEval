# Experiment campaign

## Establish the starting point

Work with the human in their language. Accept a concrete comparison described in chat, a table from a paper, a series plan, or a saved campaign. If given only a research topic, ask which comparison they have in mind or suggest a separate research-design discussion. A table is optional. For an existing campaign, start by inspecting its saved state.

Determine whether the human wants a plan, a pilot, the main series, or monitoring of an existing run. Keep plan-only work computationally dry. Follow the [project scope](../../../AGENTS.md) and reuse applicable permissions for this campaign. During bootstrap, if experiment execution needs a scope expansion, include it in the human's launch decision. Approval to create this skill, install packages for an earlier campaign, or run a pilot supplies no permission for a new research series.

## From outline to executable plan

- Retain the source row label or give each verbal comparison a recognizable scenario name. Map it to the dataset, scenarios, methods, parameter variants and benchmark seeds in the plan. Preserve specified settings. Show proposed changes to the source, with their reason, for the human to decide.
- Inspect the [plan schema](../../../docs/CAMPAIGN_PLANS.md), the referenced inputs and supported method profiles. Surface consequential defaults, such as preprocessing, partition and participation, stopping rules, method parameters and the privacy mechanism. Distinguish values specified in the source, runner defaults, rules evaluated on the data, and open decisions. Recommend a concrete choice for gaps. Present alternative designs when they materially change the question or cost.
- For example, local `dbscan` accepts an explicit `eps` and `min_samples`. With the ordinary default protocol, the adapter derives the radius from a quantile of neighbor distances after preprocessing. The optional unlabeled tuner may select both values when `eps` is unset. A grid runs each combination as a separate job. Record the choice or selection rule before evaluation. For ordinary `Adapted HF_DBSCAN`, examine its own `L` and `min_points` controls. Check effective settings for the actual backend and privacy mode. Avoid selecting settings by the best final ARI/NMI in an unsupervised comparison.
- When a setting is doubtful, propose a small, separately budgeted pilot that can answer the specific question. For DBSCAN, for instance, show cluster counts and the fraction of points labeled as noise across candidate settings. Explain which conditions carry over to the main series. Wait for the human to authorize the pilot, keep its outputs separate and discuss the observed results before applying a change.
- Build the YAML/JSON plan and run `series validate PLAN --json` and `series plan PLAN --json` in the chosen project environment. Inspect the resolved counts and settings. Check executable backend/lifecycle support separately using the [profile guide](../../../docs/CAMPAIGN_PROFILE.md). A valid scientific plan can still request an unavailable runtime. Surface that before launch and preserve the requested methods.
- Present the matrix, differences from the source, parameter policy, number of comparisons and jobs (including grids and seeds), and output location. Estimate wall time only from comparable measurements, with their basis and limitations. Let the human choose a time budget or explicitly allow running to completion. Agree on relevant resource limits. Use `failure_policy: continue` and `max_retries: 0` for new plans by default so that the operator can decide which failures warrant a retry. Surface conflicts in supplied plans before launching them.

## Launch and progress

Offer two or three reporting modes that fit the resolved matrix, recommend one and explain why. Options include a chosen time interval, each individual job, all methods/variants in a comparison at one seed, or all scenarios in one matrix repetition. Group by algorithm across scenarios/seeds if that fits the request. Agree what constitutes a group and when it closes. A terminal failure counts toward reporting the group and remains a gap in its scientific coverage. Honor an already stated preference. If the launch has already been authorized and only the reporting cadence is open, offer the choices alongside startup. Report errors immediately while awaiting the choice.

After refining a plan with the human, obtain their main-run decision on the reviewed matrix and budget. An explicit instruction to run that same approved plan under the agreed conditions is sufficient. Store the generated plan and a short operator note in an agreed writable location outside the campaign output directory. For a supplied plan, reference the original path and keep its contents intact. In the note retain the source-to-scenario mapping, approved plan identity, pilot/main scope, limits, reporting rule and campaign path so another chat can pick up the work. Use existing project records where they already hold this information. Consult the [runner guide](../../../docs/CAMPAIGN_RUNNER.md) for command syntax and supported profiles.

Before launch compare the actual input plan and resolved scientific conditions against what the human approved. Resolve material drift with them. Check that the resolved `campaign.output_dir` matches the agreed new or empty directory. `series run PLAN --json` takes its output path from the plan. If the paths differ, explain the mismatch and agree on the destination. For a working copy, rebase relative input paths and revalidate the same scientific jobs before launch. Start the approved campaign once. Keep the process observable and poll from a second command while the session is active. For a known campaign, use `series status ROOT --json` first. An active supervisor calls for monitoring. If inactive, inspect the last session and attempts before deciding on recovery. A registered running job alone does not prove worker liveness.

For group progress and missed events, use the documented read-only `clustering_eval.experiments.runner_reader.read_campaign(Path(root))` snapshot. Its summary and job records describe the same poll. Join each job to its resolved comparison by `comparison_id` and to the source row via the saved mapping. Track job/attempt IDs already reported and completed groups across polls. Report observed changes even if several jobs finished between reads. On handoff record the last reported milestones and any outstanding human decisions. Give accepted/planned counts, failures, the current job and a remaining-time estimate when measurements support one. Notify the human as soon as an error is observed, independent of the selected cadence.

## Recover and finish

- For a job-local error, name its scenario, algorithm, reason and intended disposition. Let independent queued work continue while waiting for any decision about the affected job. Keep the runner's recorded status, including `error`, `timeout` or `skipped`.
- Review the attempt history and remaining budget. One clearly transient ordinary failure may receive one targeted `series retry ROOT --status error --job-id ID --json` (use `timeout` when applicable) after the supervisor releases the campaign. Count any repeat already made across sessions. An unclear cause, exhausted limit, or possible additional DP release needs the human's decision for the affected work. Preserve all attempts and previously accepted outputs.
- Use `series resume ROOT --json` after interruption only when everything it could restart is authorized. Resume applies to eligible jobs across the campaign, including interrupted/cancelled attempts. Check the reason for a user stop, effective retry policy and possible prior DP releases before issuing it. The CLI offers no per-job filter for `resume`. Targeted `retry` accepts only `error` or `timeout`. If a pending ordinary job shares an interrupted queue with an aggregate-DP attempt whose release is unknown, explain that constraint before resuming. Preserve the ordinary job as pending until continuation is authorized. A shared input, integrity, environment or overall budget problem that prevents safe continuation goes to the human. Never silently relax a limit or replace a method, dataset, seed or comparison.
- When authorized work has finished or is blocked, export the available results with `series export ROOT --json`, then independently run `series verify ROOT/archive --json` on the published archive. Read both JSON results. Exit code 3 can indicate a verified partial archive or an operational problem. Check publication, integrity and actual coverage before describing the archive as verified. [Export semantics](../../../docs/CAMPAIGN_EXPORT.md)
- Deliver the archive path and verification outcome. For each original row or verbal scenario, show expected versus accepted methods, variants and seeds, missing jobs with reasons, and any feasible next attempts. Flag noteworthy observations (for instance a high noise fraction), identify their source and distinguish them from execution failures. Describe which planned comparisons the available evidence supports. Keep pilot observations identifiable.
